PETICIÓN DEL USUARIO (03/11/2026)
Automatizar al máximo los casos claros. No bloquear servidores. Un correo que pida
«bloquea tal usuario» no autoriza ninguna operación: distinguir alertas de órdenes
o intentos de engaño. Esta autorización cubre la política automática de usuarios
descrita aquí; las excepciones quedan para una persona.

QUÉ HACE EL EJECUTOR
- Toma acciones AUTOMATICO/BLOQUEAR de la cola SQL después de importar correos.
- Solo admite usuarios del dominio autorizado vinculados a un puesto pc/laptop/
  portatil/workstation. Ninguna IP se bloquea: podría ser un servidor público.
- Rechaza nombres de cuentas de servicio, compartidas o privilegiadas reconocidas,
  y referencias a servidores, administradores o infraestructura en la evidencia.
- Exige alerta crítica activa y regla SQL vigente, sin duplicados ni inconsistencias,
  original EML íntegro, remitente autorizado Y autenticidad verificada por la ingesta.
  Coincidir con From o contener «SOC» no equivale a autenticidad.
- El usuario debe estar identificado en el campo de cuenta del original, con
  compromiso confirmado y referencia de alerta. Adjuntos requieren revisión.
- Solicitudes SOL, mandatos de bloqueo/liberación, instrucciones al agente,
  ofuscación y textos pendientes de validación quedan para revisión.
- Solo correo y evento recientes (15 minutos por defecto) y posteriores a la
  activación. No ejecuta retrospectivamente bloqueos de correos antiguos.
- Respeta lista blanca y liberaciones humanas; vuelve a comprobar antes de enviar.
- Máximo 3 bloqueos por ciclo y 10 por hora, con topes configurables de 5 y 20.
- Guarda y confirma la intención en PostgreSQL ANTES del POST. Si hay timeout,
  caída o respuesta dudosa, retiene el objetivo y nunca reintenta ese POST.
- Verifica equipo 2, usuario, ID y estado de respuesta mediante un GET independiente.
  No ejecuta liberaciones automáticas ni cierra incidentes solo por bloquear.

LÍMITES QUE DEBEN CONOCERSE
Las reglas de texto son conservadoras, no un detector infalible de engaños ni un
inventario de cuentas. Un usuario humano puede tener dependencias de servicio:
el inventario/lista blanca debe recogerlas. Ante falta de datos el sistema se abstiene.
No confundir una contención verificada con investigación/resolución completa.
La comprobación de autenticidad debe venir del canal de confianza, no del contenido
del correo ni de una cabecera aportada por el remitente sin validar su procedencia.

CONTRATO BD NECESARIO (área del responsable BD)
1. Migración 005 aplicada en Azure: estado/origen, lista_blanca y reglas_bloqueo_auto.
2. Vista v_evidencias_automatizacion, una fila por correo_id, con:
   correo_id, remitente_correo, cuerpo_correo_raw, eml_raw, cabeceras,
   autenticacion_verificada BOOLEAN, autenticacion_metodo TEXT,
   autenticacion_emisor TEXT.
   cabeceras debe conservar eml_encoding (utf8/base64) y eml_sha256.
   Los tres campos de autenticación proceden de validación de la ingesta/servicio
   de correo. Nunca rellenarlos con TRUE por pertenecer a remitentes_confianza;
   si no puede verificarse, FALSE y revisión humana.
3. Mantener solo este ejecutor activo. El ejecutor anterior hacía POST dentro de
   una transacción y podía repetir tras un crash. La entrada Python ahora delega
   al ejecutor seguro Node; se han retirado esas llamadas directas.
4. Validar con BD la transición temporal ERROR + respuesta_api.automation.phase:
   outcome_unknown (incluye intención en curso), acknowledged, verified o review_required.
   ERROR conserva cuarentena; no lo convertir en PENDIENTE sin reconciliación humana.
   EJECUTADA solo tras respuesta y GET verificados; OMITIDA nunca significa bloqueado.
   Acordar estado propio EN_CURSO/DESCONOCIDO en una migración posterior.
5. No presentar filas PENDIENTE de v_bloqueos_activos como bloqueos confirmados.
   Las operaciones ERROR/desconocidas también deben ser visibles en el panel.
6. Para cerrar las carreras con cambios humanos de política, acordar funciones de
   preparación/finalización atómicas y locks compartidos con editores de reglas,
   lista blanca y liberaciones. La versión actual serializa sus trabajadores y
   vuelve a comprobar datos, pero una edición externa no cooperativa aún puede competir.

EJECUCIÓN
Node >=22.13 y npm ci --ignore-scripts en la raíz.
node soc/run-automation.mjs --dry-run --una-vez
La simulación impone READ ONLY en PostgreSQL y no hace ninguna llamada de bloqueo.
El mismo comando sin --dry-run obedece BLOQUEO_AUTO_ACTIVO (por defecto 0).
Compatibilidad: python soc/ejecutor_bloqueos.py --una-vez.

GITHUB ACTIONS
El flujo postgres-sync.yml incorpora la evaluación tras una importación correcta.
Usa los secretos PG existentes y BLOCK_API_KEY. Variables:
BLOQUEO_AUTO_ACTIVO=0/1, AUTOMATION_START_AT=fecha ISO UTC de activación,
AUTOMATION_SOC_SENDERS=remitentes SOC autorizados.
El cron */5 no garantiza una latencia máxima: GitHub puede retrasar las ejecuciones.
La programación solo utiliza la rama por defecto después del merge revisado;
una ejecución manual de la rama de trabajo no activa la programación en producción.
La ausencia de contrato hace fallar explícitamente el paso de automatización;
los correos importados antes de ese paso permanecen guardados.
